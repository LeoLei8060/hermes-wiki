    TLS与HTTPS握手细节¶

    iNote

    HTTPS 的本质不是“HTTP 更安全一点”，而是：**在 HTTP 之下先建立 TLS 安全通道，再在这个安全通道中传输 HTTP 数据。** 面试里真正高频被问到的是：TLS 到底在握手阶段做了什么，为什么它能同时解决机密性、完整性和身份认证问题。

    1. 先回答一个根问题：HTTPS 为什么不能只靠密码？¶

    很多初学者会想：

    既然要保密，那客户端和服务器直接约定一个密码不就行了？

    问题在于： - 这个密码怎么安全发给对方？ - 你怎么确认你连的真的是目标服务器，而不是中间人伪装的服务器？ - 每次都共用同一个长期密钥，一旦泄露怎么办？

    所以 HTTPS/TLS 需要同时解决三件事：

    1. 机密性：别人不能偷看数据
    2. 完整性：别人不能悄悄改数据
    3. 身份认证：客户端知道自己连的真是目标服务器

    2. HTTPS 和 TLS 的关系¶

    HTTPS 不是新协议壳子那么简单¶

    严格说：

    HTTPS = HTTP + TLS

    也就是说： - 应用层仍然是 HTTP - 但在发 HTTP 请求前，先完成 TLS 握手 - 后续 HTTP 数据都走加密通道

    所以：

    HTTP 决定“传什么语义”，TLS 决定“怎么安全地传”。

    可联动：HTTP与HTTPS

    3. TLS 握手到底在干什么¶

    TLS 握手的目标可以概括成四件事：

    1. 协商协议版本
    2. 协商加密套件（cipher suite）
    3. 验证服务器身份（证书）
    4. 安全地产生“后续通信用的会话密钥”

    注意：

    TLS 握手阶段主要用来“建立安全通道”，不是直接大规模传业务数据。

    4. 为什么通常是“非对称 + 对称”混合方案¶

    4.1 非对称加密的作用¶

    • 便于身份认证
    • 便于安全协商密钥

    4.2 对称加密的作用¶

    • 性能高
    • 适合后续大流量数据传输

    所以 TLS 的基本思路是： - 握手时：用非对称机制做身份验证和密钥协商 - 传输时：用对称密钥加密 HTTP 数据

    这也是为什么：

    TLS 不是“全程都用 RSA 加密业务数据”，那样太慢。

    5. TLS 1.2 时代的典型握手流程（直觉版）¶

    下面先看简化版流程：

    第一步：ClientHello¶

    客户端发： - 支持的 TLS 版本 - 支持的加密套件列表 - 一个随机数（Client Random） - 其他扩展信息（如 SNI）

    第二步：ServerHello¶

    服务端回复： - 选择使用的 TLS 版本 - 选择的加密套件 - 另一个随机数（Server Random） - 证书链 - 必要时附带密钥交换参数

    第三步：客户端验证证书¶

    客户端检查： - 证书是不是受信任 CA 签发 - 域名是否匹配 - 证书是否过期 - 证书链是否有效

    如果这里失败，浏览器就会报证书错误。

    第四步：协商预主密钥 / 共享秘密¶

    这一步具体方式取决于加密套件： - 旧方案可能基于 RSA - 更常见现代方案基于 (EC)DHE 密钥交换

    第五步：双方推导会话密钥¶

    双方各自基于： - Client Random - Server Random - 共享秘密

    推导出后续通信用的对称密钥。

    第六步：Finished¶

    双方用新协商出的密钥验证“握手过程没有被篡改”，确认进入加密通信阶段。

    之后 HTTP 请求/响应才真正开始走加密通道。

    6. TLS 1.3 为什么更先进¶

    TLS 1.3 相对 TLS 1.2 的重要变化包括：

    6.1 握手更短¶

    • 减少 RTT
    • 建连更快

    6.2 去掉很多老旧、不安全算法¶

    例如： - 弱 RSA 密钥交换方式 - 某些历史兼容算法

    6.3 更强调前向保密（Forward Secrecy）¶

    现代握手更多基于 ECDHE。

    这意味着：

    即使服务器长期私钥将来泄露，也不应该让历史抓包流量全部被解开。

    这是面试里非常值得提的点。

    7. 证书在这里扮演什么角色¶

    7.1 证书不是“用来直接加密全部数据”的核心¶

    证书更核心的作用是：

    证明服务端身份。

    证书里面通常包含： - 服务器公钥 - 域名信息 - 颁发者信息 - 有效期 - CA 的数字签名

    7.2 客户端为什么会信证书¶

    因为客户端本地内置了受信任 CA 根证书列表。 它会验证： - 当前站点证书是不是由受信任 CA 签名 - 链路是不是完整可信

    7.3 自签证书为什么会报警告¶

    因为浏览器/系统默认不信它。 不是因为“加密一定无效”，而是因为： - 身份认证链条不被系统信任

    8. 为什么 TLS 能防中间人攻击（MITM）¶

    如果没有证书验证，攻击者可以： - 冒充服务器 - 和客户端建立连接 - 再转发给真实服务器

    TLS 的关键在于： - 服务端必须出示有效证书 - 客户端会校验证书链和域名 - 攻击者没有对应私钥，就无法伪造一个受信任且域名匹配的证书

    所以：

    TLS 能防 MITM，不是因为“加密了”，而是因为“先认证了对方身份，再建立了密钥”。

    这个点非常关键。

    9. TLS 为什么还能保证完整性¶

    除了加密，TLS 还要确保： - 数据在传输中没被改

    因此它会使用： - MAC（旧模型） - 或 AEAD（如 AES-GCM、ChaCha20-Poly1305）

    这样接收端可以检测： - 数据是否被篡改 - 报文是否完整

    所以： - 机密性 ≠ 完整性 - TLS 两者都要保证

    10. 一个直观类比¶

    可以把 TLS 握手理解成：

    普通 HTTP¶

    像你把明信片直接寄出去： - 路上谁都能看 - 谁都能改 - 你也不一定知道收件人是不是被掉包了

    HTTPS / TLS¶

    像你先： 1. 验证对方身份证明 2. 协商一个只有你们知道的临时密码本 3. 后续都按这个密码本加密对话

    这时别人： - 看不懂内容 - 改了也会被发现 - 冒名顶替也更难成功

    11. 工程上常见的问题¶

    11.1 证书错误¶

    常见原因： - 域名不匹配 - 证书过期 - 证书链不完整 - 自签证书未被信任

    11.2 HTTPS 很慢¶

    常见原因未必是“加密太重”，也可能是： - 频繁新建连接 - TLS 握手 RTT 高 - 证书链/OCSP/网络质量问题

    11.3 明明是 HTTPS 还是被代理抓包¶

    如果客户端信任了代理安装的根证书，代理可以作为“受信任 CA”中间解密再转发。 所以 HTTPS 不是“绝对不可见”，而是“前提是信任链不被篡改”。

    12. Qt / C++ 里和 TLS 有关的东西¶

    在 Qt 项目里，HTTPS 常通过： - QNetworkAccessManager - QSslConfiguration - QSslSocket

    在通用 C++ 里可能通过： - OpenSSL - Boost.Asio + OpenSSL - Poco::Net - libcurl

    你在工程里经常遇到的问题是： - 证书校验失败 - TLS 版本兼容失败 - 自签证书开发环境怎么接入

    13. 面试回答模板¶

    TLS 握手的核心目标是协商出一个安全的会话密钥，并验证服务器身份。客户端先发 ClientHello，服务端返回 ServerHello 和证书，客户端验证证书链和域名是否合法，然后双方通过密钥交换算法（现代一般是 ECDHE）协商共享秘密，再基于随机数和共享秘密推导出后续通信使用的对称密钥。之后 HTTP 数据通过这个加密通道传输。HTTPS 能保证机密性、完整性和身份认证，其中防中间人攻击的关键不是单纯加密，而是证书和身份验证机制。

    14. 初学者最容易犯的错误¶

    14.1 误以为 HTTPS = HTTP 加个锁图标¶

    错。核心在 TLS 握手和证书信任链。

    14.2 误以为证书就是“加密内容”本身¶

    证书更核心是用来做身份认证。

    14.3 误以为 HTTPS 完全靠 RSA 加密所有数据¶

    错。现代 TLS 主要是： - 握手协商 - 后续用对称密钥传输

    14.4 误以为只要加密了就能防中间人攻击¶

    错。必须有身份认证链条才行。
