    DNS协议¶

    iNote

    DNS（Domain Name System）的核心作用是：**把人类容易记住的域名，转换成机器可以真正通信的 IP 地址。** 但它远不只是“查个 IP”，而是一整套分布式命名系统，包含层级结构、缓存机制、记录类型、递归/迭代查询流程等内容。

    1. 先回答最基础的问题：为什么需要 DNS？¶

    人类更适合记： - www.example.com - api.company.com

    机器网络通信真正用的是： - 93.184.216.34 - 2400:3200::1

    所以 DNS 解决的第一层问题是：

    名字到地址的映射。

    如果没有 DNS： - 每次访问网站都要记 IP - IP 一变，用户就全断 - 很难做负载均衡、容灾切换和服务迁移

    所以 DNS 的意义不只是“方便记忆”，更是： - 支撑大规模互联网命名体系 - 把“服务标识”和“机器地址”解耦

    2. DNS 是什么结构？¶

    DNS 本质上是一个分层的分布式数据库。

    2.1 层级结构¶

    典型域名：

    www.example.com.

    可以拆成： - . 根域 - com 顶级域 - example 二级域 - www 主机名或子域名

    也就是说，DNS 是树形层级命名系统，不是平面列表。

    2.2 为什么要做成分层的¶

    如果全世界所有域名都靠一个中心服务器维护： - 无法扩展 - 单点故障严重 - 管理成本极高

    分层后： - 根域只管顶级域信息 - 顶级域服务器只管下一级授权 - 每一层只维护自己负责的那部分数据

    这使 DNS 可以全网扩展。

    3. DNS 查询到底是怎么走的¶

    一个典型 DNS 查询大致可以分成两类角色：

    3.1 递归查询（Recursive Query）¶

    客户端通常是这样想的：

    “我只问你一次，你帮我把最终答案查回来。”

    这个“你”通常是： - 操作系统配置的本地 DNS - 路由器 DNS - 公共 DNS（如 8.8.8.8） - 企业内网 DNS

    3.2 迭代查询（Iterative Query）¶

    DNS 服务器彼此之间更常见的是：

    “我不知道最终答案，但我告诉你下一步该去问谁。”

    4. 一次完整的 DNS 解析流程¶

    假设浏览器访问：

    www.example.com

    第一步：查本地缓存¶

    浏览器 / 操作系统 / 本地 resolver 先看缓存里有没有。

    第二步：问本地 DNS 服务器¶

    如果没有，就向配置好的 DNS 服务器发起查询。

    第三步：本地 DNS 去问根服务器¶

    根服务器通常不会直接给出目标 IP， 它会说：

    “.com 这个顶级域该去问这些服务器。”

    第四步：去问 .com 顶级域服务器¶

    .com 服务器会说：

    “example.com 这个域名该去问这些权威服务器。”

    第五步：去问 example.com 的权威 DNS¶

    权威 DNS 才真正返回： - www.example.com -> 93.184.216.34

    第六步：结果回给客户端，并写入缓存¶

    本地 DNS 把结果返回给客户端，同时缓存一段时间。

    5. 权威 DNS 和本地 DNS 有什么区别¶

    本地 DNS（递归解析器）¶

    作用： - 替客户端查答案 - 做缓存 - 减少重复查询开销

    权威 DNS（Authoritative DNS）¶

    作用： - 持有某个域名的“最终记录” - 是这个域名数据的权威来源

    所以：

    本地 DNS 更像“查询代理 + 缓存层”，权威 DNS 更像“官方数据源”。

    6. 常见记录类型¶

    这是面试和工程里都常问的内容。

    6.1 A 记录¶

    把域名映射到 IPv4 地址。

    example.com -> 1.2.3.4

    6.2 AAAA 记录¶

    把域名映射到 IPv6 地址。

    6.3 CNAME 记录¶

    别名记录。

    www.example.com -> example.com

    它不是直接给 IP，而是指向另一个域名。

    6.4 MX 记录¶

    邮件交换记录，用于指定邮件服务器。

    6.5 NS 记录¶

    指定某个域名由哪些 DNS 服务器负责。

    6.6 TXT 记录¶

    文本记录，常用于： - 域名验证 - SPF / DKIM / DMARC - 自定义说明信息

    7. TTL 是什么，为什么重要¶

    TTL（Time To Live）表示：

    一条 DNS 记录允许被缓存多长时间。

    TTL 大的好处¶

    • 减少 DNS 查询量
    • 提高解析速度

    TTL 大的坏处¶

    • 切换 IP 时生效慢
    • 故障切换不灵活

    所以工程上经常要权衡： - 稳定服务时：TTL 可以大一点 - 切流/迁移/容灾前：TTL 会提前调小

    8. 为什么 DNS 常用 UDP？¶

    经典 DNS 查询常用 UDP，原因很直接： - 请求报文通常小 - 单次收发就能完成 - 无需建立连接，延迟低

    这对“高频、小包、快速应答”的 DNS 场景很合适。

    但 DNS 不只用 UDP¶

    以下情况可能用 TCP： - 响应太大，超出 UDP 适合范围 - 区域传送（zone transfer） - 某些安全扩展或特殊实现场景

    所以正确说法是：

    DNS 查询通常优先走 UDP，但并不排斥 TCP。

    9. 递归查询 vs 迭代查询，面试怎么答¶

    这是高频点。

    递归查询¶

    客户端问本地 DNS：

    “你直接把最终结果给我。”

    迭代查询¶

    DNS 服务器之间互相问时：

    “我不知道最终结果，但我告诉你下一步去哪查。”

    一句话记忆¶

    • 递归：替你查到底
    • 迭代：告诉你下一跳

    10. 缓存为什么是 DNS 的关键¶

    如果每次都从根域一路查到底： - 很慢 - 根服务器压力巨大 - 重复查询浪费严重

    所以 DNS 性能很大程度上依赖缓存： - 浏览器缓存 - 操作系统缓存 - 本地 DNS 缓存

    缓存带来的问题¶

    • IP 已经切换，但用户还在用旧结果
    • 局部地区缓存污染导致结果异常
    • TTL 配置不合理导致生效慢

    11. 工程上最常见的 DNS 问题¶

    11.1 域名解析失败¶

    可能原因： - 域名配置错 - 本地 DNS 配置错 - 权威服务器异常 - 网络到 DNS 服务器不通

    11.2 域名能 ping 通，但业务还是不通¶

    说明 DNS 只是第一步，后面还可能有： - TCP 端口未开放 - HTTPS 证书不匹配 - 反向代理配置错误

    11.3 切流后仍访问旧 IP¶

    典型原因： - TTL 太长 - 本地 / 浏览器 / 运营商 DNS 还没刷新

    11.4 某些地区正常，某些地区异常¶

    常见于： - 运营商 DNS 差异 - CDN 调度问题 - GeoDNS 策略问题

    12. 常见排查命令¶

    nslookup¶

    快速查域名解析结果。

    dig¶

    Linux/Unix 下更强大的 DNS 工具。 可看： - A / AAAA / MX / NS / TXT - 权威应答 - TTL - 查询路径

    ping¶

    不是查 DNS 协议本身，但能间接验证解析结果是否可达。

    tracert / traceroute¶

    用于进一步判断网络路径问题。

    可联动：常见网络故障排查

    13. DNS 和 HTTP / HTTPS 的关系¶

    用户访问：

    https://www.example.com

    一般先发生： 1. DNS 解析：www.example.com -> IP 2. TCP 建连 3. TLS 握手（如果是 HTTPS） 4. HTTP 请求/响应

    所以：

    DNS 通常是很多 Web 请求链路的第一步。

    如果 DNS 失败，后面 TCP / TLS / HTTP 都无从谈起。

    可联动： - HTTP与HTTPS - TLS与HTTPS握手细节

    14. 初学者最容易犯的错误¶

    14.1 误以为 DNS 只是“域名查 IP”¶

    这是最表层的理解。更深层它是分层、分布式、可缓存的命名系统。

    14.2 误以为 DNS 只有一个服务器¶

    错。它是： - 根域 - 顶级域 - 权威 DNS - 本地解析器

    共同协作的体系。

    14.3 误以为 DNS 查出来就代表网站能访问¶

    错。解析成功只说明“名字找到了地址”，不代表： - 端口通 - TLS 正常 - 应用层服务正常

    14.4 误以为 DNS 一定走 UDP 且永远不用 TCP¶

    也不对。通常走 UDP，但某些情况会用 TCP。

    15. 面试回答模板¶

    DNS 是一个分层的分布式命名系统，核心作用是把域名解析成 IP 地址。一次典型解析会先查本地缓存，再问本地 DNS 服务器，本地 DNS 再通过根域、顶级域和权威 DNS 逐步找到最终记录并缓存结果。常见记录类型包括 A、AAAA、CNAME、MX、NS、TXT。DNS 查询通常优先用 UDP，因为报文小、延迟低，但某些场景也会用 TCP。理解 DNS 的关键在于分层结构、缓存机制、递归与迭代查询流程。
