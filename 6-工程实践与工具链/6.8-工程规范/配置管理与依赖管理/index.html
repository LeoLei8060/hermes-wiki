    配置管理¶

    Note

    配置管理解决的是配置来源、作用域、变更和回滚问题，目标是让部署和运维行为可预测、可追溯。

    1. 知识点说明¶

    配置管理关注：配置文件从哪里读取（本地文件/环境变量/配置中心/命令行参数）、不同环境（开发/测试/生产）如何隔离配置、配置变更如何记录和回滚、敏感配置（密钥/密码）如何安全存储。它直接影响部署稳定性——线上故障中相当比例来自配置错误。

    2. 核心概念¶

    • 配置分层：按优先级合并多个配置源（命令行 > 环境变量 > 配置文件 > 默认值），保证 override 行为可预期
    • 环境隔离：dev/staging/prod 各自独立的配置，绝不共用同一份配置数据
    • 敏感项脱敏：密钥、密码等不得明文存入仓库，应通过密钥管理服务（如 Vault）或环境变量注入
    • 变更可追踪可回滚：配置变更应有审计日志，支持一键回滚到上一个已知良好版本

    3. 代码示例¶

    3.1 分层配置读取¶

    // 优先级：env > config file > default
int GetPort() {
    const char* envPort = std::getenv("APP_PORT");
    if (envPort) return std::stoi(envPort);
    return config.GetInt("server.port", 8080);  // 默认值兜底
}

    3.2 环境变量覆盖¶

    export APP_LOG_LEVEL=INFO
export APP_DB_HOST=db-prod.internal
export APP_SECRET_KEY=$(vault read -field=key secret/app)

    分层的关键是：上层覆盖下层，但覆盖规则要统一、透明。

    4. 底层原理 / 实现机制¶

    配置管理的核心数据结构是优先级排序的 key-value 映射表。读取流程为：

    1. 各配置源按优先级顺序依次解析（文件用 YAML/JSON/TOML 解析器，环境变量按命名规则映射）
    2. 后面解析的值覆盖前面的同 key 值
    3. 敏感字段可标记为"仅运行时加载"，不写入配置文件
    4. 动态更新依赖文件监听（inotify）或配置中心长轮询推送，更新后触发回调重载业务组件

    5. 常见问题¶

    编码陷阱¶

    • 配置文件带密钥入库：在 .gitignore 中排除 secrets 文件，用 .env.example 模板代替，真实值由 CI/CD 或配置中心注入
    • 生产环境用了开发配置：部署脚本缺少环境判断，一旦 DEV 环境的 mock 数据库地址跑到 PROD 就是故障。应通过 ENV=production 强制指定配置目录
    • 配置热更新未做原子替换：更新一半时服务读到不完整的配置。应使用双缓冲或原子写入（写临时文件再 rename）

    概念误区¶

    • "一个配置文件就够了" → 当需要灰度发布或 A/B 测试时，单文件无法按用户/流量维度区分配置
    • "配置中心就是远程 JSON 文件" → 配置中心的核心价值是灰度发布、审批流、回滚和审计，而不只是"放文件"

    • 文档规范 — 配置项含义、默认值、生效范围需要文档化

    依赖管理¶

    Note

    依赖管理的关键不是"能编过"，而是版本、来源和升级路径可控——构建可复现和供应链安全都依赖于此。

    1. 知识点说明¶

    依赖管理关注：第三方库和内部库的引入方式（源码编译/预编译包/包管理器）、版本锁定策略（精确版本 vs 范围版本）、依赖更新与兼容性评估、以及传递依赖的可见性和冲突解决。它直接决定了构建的可复现性——"上个月能编过的代码今天编不过"几乎都是依赖问题。

    2. 核心概念¶

    • 依赖来源明确：每个依赖从哪来（Git URL / Conan / vcpkg / 系统包管理器 / 源码嵌入）必须有据可查
    • 版本锁定：lock 文件（如 conan.lock / vcpkg.json）记录精确版本，保证团队和 CI 的一致性
    • 最小依赖原则：只引入真正需要的库，每个额外依赖都是维护负担、编译时间开销和攻击面
    • 升级路径可评估：新版本变更日志（changelog）应说明 breaking changes，团队应定期评估依赖升级

    3. 代码示例¶

    3.1 CMake 引入依赖（Import Target）¶

    find_package(fmt 10.1 REQUIRED)
target_link_libraries(app PRIVATE fmt::fmt)

    Import Target fmt::fmt 自动携带头文件路径和链接库，优于手写 include_directories + link_libraries。

    3.2 vcpkg 清单模式锁定版本¶

    {
  "name": "my-project",
  "version": "1.0.0",
  "dependencies": [
    { "name": "fmt", "version>=": "10.1.0" },
    { "name": "openssl", "version>=": "3.0.0" }
  ],
  "builtin-baseline": "abc123def..."
}

    builtin-baseline 锁定整个 vcpkg registry 的快照版本，确保所有依赖的可复现。

    4. 底层原理 / 实现机制¶

    依赖管理解决的核心问题是"菱形依赖"：A 依赖 B 和 C，B 和 C 又各自依赖 D 的不同版本。解决策略包括：

    1. 版本约束求解：包管理器（如 Conan/vcpkg）用 SAT 求解器计算兼容版本组合
    2. 传递依赖可见性：CMake 的 PRIVATE 依赖不传播给下游，PUBLIC 才传播
    3. vendoring（源码嵌入）：将关键依赖的源码直接纳入项目仓库，消除外部依赖的不确定性，代价是手动维护更新

    5. 常见问题¶

    编码陷阱¶

    • 不锁版本，用 latest 或范围版本：CI 某天突然编译失败，因为某个依赖发布了不兼容的新版。必须锁定精确版本或基线
    • 头文件依赖未用 PRIVATE：内部实现的依赖（如测试框架）用 PUBLIC 暴露给下游，导致使用方也被迫引入无关库
    • 依赖冲突静默忽略：链接时某个库的符号被另一个版本的同名库覆盖（ODR violation），程序行为不可预测

    概念误区¶

    • "依赖越多功能越强" → 每个依赖都是编译时间、二进制体积、许可证合规和 CVE 修复的成本
    • "编译通过就是兼容的" → ABI 兼容和 API 兼容是两回事，运行时崩溃往往来自 ABI 不匹配

    6. 相关知识点¶

    • find_package — CMake 依赖发现机制的核心
    • install与package — 安装导出使自己的库能作为他人的依赖
    • 模块化设计 — 模块划分直接影响依赖图的健康度

    源3：文档规范¶

    文档规范¶

    Note

    文档规范的目标不是写更多文档，而是让关键信息可查、可用、可更新——文档的生命力在于维护而非创建。

    1. 知识点说明¶

    文档规范定义项目应维护哪些文档（README / 架构设计 / API 文档 / 部署手册 / 变更记录 / 排障手册）、每类文档的内容结构、存放位置、更新触发条件和责任人。好的文档体系让新人快速上手、让故障快速定位、让交接不再依赖口头传承。

    2. 核心概念¶

    • 文档面向读者场景，而非作者视角：部署文档写给运维不是写给开发者，API 文档写给调用方不是写给实现者
    • 关键操作步骤必须可执行：每条命令应可直接复制运行，不能有"安装相关依赖"这种模糊描述
    • 设计要与实现同步更新：代码 merge 后，对应的设计文档、API 文档应同步 PR 更新，而非"以后补"
    • 过期文档比没有文档更危险：过期的接口文档可能误导调用方写出 bug。无法维护的文档宁可删除并注明"参见代码"

    3. 代码示例¶

    3.1 README 最小模板¶

    # Project Name
> 一句话说清项目做什么

## 快速开始
git clone ... && cd project && cmake -B build && cmake --build build

## 构建
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release

## 运行
./build/bin/app --config config/prod.yaml

## 目录结构
src/       — 源码
include/   — 公共头文件
docs/      — 详细文档
tests/     — 测试

    3.2 变更记录规范¶

    ## [1.3.0] - 2026-07-08
### Added
- 支持 OAuth2 登录
### Changed
- 数据库连接改为连接池模式
### Fixed
- 修复并发写入时偶发死锁

    采用 Keep a Changelog 格式，方便自动生成 release notes。

    4. 底层原理 / 实现机制¶

    文档工程的核心理念是"文档即代码"（Docs as Code）：文档用 Markdown/reStructuredText 编写，跟代码存在同一仓库，通过 PR 评审，通过 CI 构建发布（如 MkDocs / Docusaurus / GitBook），版本与代码 release 绑定。这解决了三大问题：

    1. 文档与代码版本同步——不会有"文档说的是 v1.0 的接口，代码已经是 v2.0"
    2. 文档有评审机制——错别字、过时信息在 PR 阶段被拦截
    3. 文档可自动发布——push 即更新，无需手动上传

    5. 常见问题¶

    编码陷阱¶

    • 文档中的代码示例未经验证：示例中的 API 名、参数类型跟实际代码不一致，读者照着写编译不过。应在 CI 中编译文档中的代码片段
    • README 只写"如何构建"不写"为什么这么构建"：架构决策记录（ADR）缺失，后来者不理解为什么选了某种方案，可能在重构时踩同样的坑
    • 接口文档靠人工维护而非自动生成：每次接口变更后文档忘记更新。应用 Doxygen/Sphinx 从代码注释自动生成 API 文档

    概念误区¶

    • "好代码自解释，不需要文档" → 代码解释"怎么做"，文档解释"为什么做"和"怎么用"。架构决策、设计意图、业务背景是代码表达不了的
    • "文档写完就完了" → 文档是活的东西，需要像代码一样持续维护和更新，否则迅速贬值

    6. 相关知识点¶

    • README — 项目入口文档的编写规范
    • tag与Release — Release Notes 是文档的重要组成部分
    • 命名规范 — 好的命名让代码自文档化，减少对注释的依赖

    7. 面试点¶

    7.1 高频问题¶

    • 你参与过的项目有哪些类型的文档？文档和代码如何保持同步？
    • 接手一个没有文档的遗留项目，你从哪开始补文档？
    • API 文档是手写还是自动生成？各自优缺点？

    7.2 回答要点¶

    • 列举类型（README/架构设计/API/部署手册/变更记录/ADR），说明通过"文档即代码"（跟代码同仓库、同 PR 流程）保持同步
    • 优先补 README（构建+运行）和部署手册（让项目可运行），再补架构概览（让代码可理解），最后补 API 文档
    • 自动生成（Doxygen/Sphinx/docfx）：始终与代码同步但格式固定、难以补充设计意图。手写：表达自由但容易过时。最佳实践：自动生成 API 骨架 + 手写关键设计说明

    7.3 深挖方向¶

    • ADR（架构决策记录）的编写格式和使用场景
    • Docs as Code 工作流：Markdown + Git + CI + 静态站点生成器
    • API 文档标准：OpenAPI/Swagger、IDL 驱动的文档生成
