    Core Dump分析¶

    Note

    Core dump 的价值不在文件本身，而在于你是否保留了对齐的符号表、正确的二进制版本和足够的上下文信息——三者缺一，它就是一块无用的磁盘占用。

    1. 知识点说明¶

    Core dump 是操作系统在进程因信号（SIGSEGV、SIGABRT、SIGFPE 等）异常终止时，将进程地址空间的完整快照写入磁盘的文件。它包含：所有内存映射区域（代码段、数据段、堆、栈）、CPU 寄存器状态、打开的文件描述符列表、信号信息。通过 GDB/LLDB 加载 core dump 和对应的可执行文件，可以离线还原崩溃瞬间的完整调用栈和变量状态。

    2. 核心概念¶

    • core 文件的生成条件：ulimit -c 控制 core 文件大小限制（unlimited 启用）、/proc/sys/kernel/core_pattern 控制文件路径和命名模板（%e=程序名 %p=PID %t=时间戳）
    • 符号匹配是核心约束：GDB 加载 core 时需要与生成 core 时完全相同的二进制（或至少保留 debug symbol 的未 strip 版本）。二进制不同（重新编译）导致地址偏移不匹配，bt 显示混乱的调用栈
    • 系统级 core 管理：systemd 的 coredumpctl 接管了传统的 core 文件，coredumpctl list 列出所有崩溃记录，coredumpctl gdb <PID> 直接用 GDB 打开
    • minidump 格式：Windows 使用 minidump（.dmp），Linux 的 Breakpad/Crashpad 也生成 minidump；可用 minidump_stackwalk 或 GDB 分析

    3. 代码示例¶

    3.1 启用 core dump¶

    # 当前 shell 启用 core dump（不限大小）
ulimit -c unlimited

# 设置 core 文件路径（包含 PID 和时间戳，避免覆盖）
echo "/tmp/core.%e.%p.%t" | sudo tee /proc/sys/kernel/core_pattern

# systemd 环境查看
coredumpctl list
coredumpctl info <PID>

    3.2 用 GDB 分析 core¶

    # GDB 加载 core 和对应 binary
gdb /path/to/myapp /tmp/core.myapp.12345.1620000000

# GDB 会话
(gdb) bt full               # 完整调用栈 + 每帧局部变量
(gdb) info registers        # 崩溃瞬间的 CPU 寄存器
(gdb) frame 0               # 切到崩溃点所在的栈帧
(gdb) info locals           # 崩溃帧的局部变量
(gdb) x/10i $rip            # 崩溃地址附近的指令
(gdb) info threads          # 所有线程的栈
(gdb) thread apply all bt   # 所有线程的调用栈

    3.3 systemd 直接启动 GDB¶

    # systemd 管理下的便捷方式
coredumpctl gdb 12345       # 自动找到 binary 并启动 GDB

# 列出最近崩溃
coredumpctl list --since=today

    4. 底层原理 / 实现机制¶

    Core 文件生成流程：

    1. 进程收到致命信号（如 SIGSEGV），内核的 do_coredump() 被调用
    2. 内核检查 ulimit -c 是否允许生成 core（0 = 禁止）
    3. 内核根据 core_pattern 决定输出路径：如果以 | 开头，将 core 管道传递给指定程序（如 systemd-coredump）；否则直接写文件
    4. Core 文件以 ELF 格式写入：包含 PT_NOTE 段（信号信息、寄存器）、PT_LOAD 段（每个内存映射区域的原始数据）
    5. 如果配置了 coredump_filter（/proc/<pid>/coredump_filter）可以排除特定类型的映射（如共享内存、文件映射），减小 core 体积

    符号解析：GDB 加载 core 时，从 core 文件的 PT_NOTE 中读取崩溃时的 rip（指令指针）和各寄存器。通过 binary 的 .debug_info（DWARF）将 rip 映射到源码行号，通过 .debug_frame（CFI）回溯调用栈：每帧记录了返回地址在栈上的偏移，CFI 表告诉 GDB 如何从当前 rsp/rbp 恢复上一帧的寄存器。

    5. 常见问题¶

    编码陷阱¶

    • 二进制和 core 版本不匹配：开发机上重新编译后拿生产的 core 分析，GDB 显示乱的调用栈或 ??。解决：在 CI 中归档每次 release 的未 strip binary（带符号），与生成的 core 配对
    • core 被截断：ulimit -c 设置不够大，或磁盘空间不足，core 文件不完整。GDB 加载时报 core file may be truncated
    • core 被 systemd 接管后找不到：/var/lib/systemd/coredump/ 下的文件是压缩格式（xz），需通过 coredumpctl 访问而非直接 gdb
    • 守护进程的 core 落在奇怪路径：core_pattern 如果设为 /tmp/core，所有 core 互相覆盖。务必在 core_pattern 中包含 %p（PID）或 %t（时间戳）

    概念误区¶

    • "只要启用 core dump 就能分析线上问题" → 需要确保二进制符号可用、glibc 等共享库的 debuginfo 包已安装（debuginfo-install glibc），否则 bt 中系统库部分显示 ??
    • "core 很大所以只适合小进程" → 可以配置 coredump_filter 排除文件映射和共享内存，只保留堆和栈；大型进程的 core 可用 gcore <pid> 手动生成

    7. 面试点¶

    7.1 高频问题¶

    • 如何确保生产环境的 core dump 可以被有效分析？需要哪些配套措施？
    • core dump 文件里包含哪些内容？用什么格式存储？
    • systemd 的 coredumpctl 做了什么？和传统 core 文件管理有什么区别？
    • GDB 加载 core 时提示 "no debugging symbols found" 或栈回溯全是 ??，问题出在哪里？

    7.2 回答要点¶

    • 三个要素缺一不可：（1）ulimit -c unlimited + core_pattern 含 PID；（2）CI 归档每次 release 的未 strip 二进制；（3）安装对应 glibc 等系统库的 debuginfo 包
    • ELF 格式：PT_NOTE 含信号、寄存器、auxv；PT_LOAD 含每个映射区域的原始内存数据；不含 swap 出的页面
    • systemd-coredump 通过 core_pattern=|/... 管道接收 core，压缩存储到 journal，通过 coredumpctl 提供统一查询接口，避免磁盘被 core 堆满
    • 最常见原因：重新编译了 binary 导致调试符号中的地址和 core 中的地址不匹配。必须使用生成 core 时的同一份 binary（或者仅 strip 符号但保留了独立的 .debug 文件，GDB 可通过 set debug-file-directory 加载）

    7.3 深挖方向¶

    • Breakpad/Crashpad 的 minidump 格式与 ELF core 的差异
    • coredump_filter 的 bitmask 控制：排除共享内存（bit 1）、文件映射（bit 4）以缩减 core 大小
    • 在线服务的 core dump 自动化收集：core_pattern 管道到上传脚本（AWS S3 / 内部存储）

    崩溃定位方法¶

    Note

    崩溃定位不是"打开 GDB 看一眼 bt"——它是有套路的：从信号类型缩小方向，从 core dump 还原现场，从最近改动锁定嫌疑人。

    1. 知识点说明¶

    崩溃定位是系统性地将程序异常终止（段错误、非法指令、断言失败、未处理异常等）追溯到根本原因的工作流程。它不依赖单一工具，而是组合使用信号分析、core dump 回溯、日志关联、版本比对、二分定位等手段，形成从现象到根因的推理链条。高效的崩溃定位需要预先建立崩溃收集基础设施（core_pattern 管道上传 + 符号服务 + 版本-二进制映射）。

    2. 核心概念¶

    • 信号类型即方向：SIGSEGV = 非法内存访问（空指针、越界、use-after-free）；SIGABRT = 主动终止（assert 失败、std::abort()、double-free 被 glibc 检测）；SIGFPE = 算术异常（除零、整数溢出被 -ftrapv 捕获）；SIGILL = 非法指令（代码段被破坏、CPU 不支持该指令、未定义行为导致的奇怪代码生成）
    • 二分法定位改动：如果崩溃在某版本后出现，git bisect 二分查找引入 bug 的 commit。比人工遍历日志高效得多
    • 输入还原：如果能复现崩溃，最小化触发输入（缩小到最短的请求/文件/消息），定位问题参数；如果不能复现，core dump 是唯一线索
    • 时间线关联：崩溃时间和部署时间、配置变更时间、流量变化时间的相关性，通常指向外部触发因素

    3. 代码示例¶

    3.1 标准崩溃定位流程¶

    # 步骤1：识别信号
# dmesg 或 journalctl 查看
journalctl -u myapp --since "5 minutes ago" | grep -E "signal|segfault|SIG"

# 步骤2：获取 core dump
coredumpctl list                              # systemd 环境
ls -la /tmp/core.*                            # 传统 core

# 步骤3：GDB 分析
gdb /path/to/exact/binary /tmp/core.xxx
(gdb) bt full                                  # 完整栈
(gdb) info registers                           # 寄存器（关注 rip/rsp）
(gdb) frame 0
(gdb) print *this                              # C++ 对象状态
(gdb) print container.size()                   # 容器是否合法

# 步骤4：地址反向映射
# 如果 binary 被 strip，用 addr2line
addr2line -e /path/to/exact/binary -f 0x401234

# 步骤5：二分定位改动（如果跟版本相关）
git bisect start
git bisect bad  HEAD
git bisect good v1.2.3
# 每次标记后重新构建和测试

    3.2 用 ASan 重现崩溃¶

    # 如果崩溃难以直接复现，用 ASan 编译后重试
cmake -DCMAKE_CXX_FLAGS="-fsanitize=address -g -O1" ..
make -j$(nproc)
# ASan 会将随机崩溃转化为精确报错，直接定位到源代码行
./myapp --input crashing_payload.txt

    4. 底层原理 / 实现机制¶

    崩溃定位的本质是从崩溃瞬间的状态反推导致崩溃的事件链。以最常见的 SIGSEGV 为例：

    1. CPU 执行 mov [rax], rbx 时，MMU 发现 rax 指向的虚拟地址没有映射或权限不匹配，触发 page fault
    2. 内核的 page fault handler 检查：地址是否在 vm_area_struct 范围内、权限是否匹配（写操作需要写权限）。如果非法，向进程发送 SIGSEGV，si_addr 字段记录非法地址
    3. 内核的 do_coredump() 在进程终止前保存内存快照
    4. 开发者通过 GDB 加载 core：bt 显示调用路径，info registers rax 显示写入的目标地址，print ptr 显示指针值——逻辑链还原：为什么 rax 是这个值？是空指针、野指针还是越界偏移？

    栈破坏的特殊情况：如果崩溃是栈缓冲区溢出导致的（覆盖了返回地址），bt 显示的是被破坏的调用栈，无法直接定位。需要 info frame 检查 saved rip 的合法性，或通过 x/s $rsp 检查栈上字符串找到线索。

    5. 常见问题¶

    编码陷阱¶

    • 只看崩溃点不看调用链：崩溃在 memcpy(dst, src, n) 但不代表 memcpy 有 bug——可能是上游传入了错误的 n 或悬空的 src。沿 bt 向上追踪参数来源
    • 用错误的 binary 分析 core：GDB 加载时不报错但显示错误的调用栈和变量值。建立 binary + debug symbol 的归档机制，确保 core 和 binary 成对存储
    • 未建立崩溃收集基础设施：线上崩溃靠用户截图反馈，信息不足无法定位。部署 core_pattern 管道上传 + Sentry/Breakpad 等崩溃收集 SDK
    • 忽略多线程崩溃：崩溃线程的栈是直接原因，但根因可能是另一个线程破坏了共享数据。thread apply all bt 检查所有线程状态

    概念误区¶

    • "只要能复现就能定位" → 有些崩溃是时间敏感的竞态条件，复现率极低。需要靠 core dump + 日志推断，而非等待复现
    • "崩溃地址 = bug 位置" → 崩溃地址只是症状。SIGSEGV at 0x0 之后要追问：哪个变量是 nullptr？它在哪里初始化？为什么没初始化？

    7. 面试点¶

    7.1 高频问题¶

    • 线上服务突然崩溃，你拿到一个 core dump，请描述完整的定位流程。
    • SIGSEGV、SIGABRT、SIGFPE、SIGILL 分别由什么常见原因触发？优先排查方向？
    • 如何在不重现崩溃的情况下定位根因？
    • git bisect 的工作流程？如何自动化？
    • 栈被破坏（stack corruption）导致 bt 显示混乱，如何进一步定位？

    7.2 回答要点¶

    • 流程：确认信号类型（dmesg/journalctl）→ 加载 core（GDB bt full + info registers）→ 从崩溃帧向上追踪参数来源 → 关联日志和部署时间线 → 二分定位改动 commit
    • SIGSEGV：非法内存访问（空指针/野指针/越界），先看 si_addr 判断是 null 还是野指针；SIGABRT：assert 失败、double-free、std::terminate，看 core 中 __assert_fail 的参数；SIGFPE：除零或整数溢出，检查运算操作数；SIGILL：执行了 non-code 内存或非法指令，看 rip 指向的地址是否在合法代码段
    • 依赖 core dump 的栈回溯 + 变量检查推断参数来源，结合日志重建事件时间线，通过代码审查看可能路径。如果无法获取足够信息，在怀疑区域加 ASan 或额外日志部署后等待下次出现
    • git bisect start → git bisect bad + git bisect good <known-good> → 逐个标记或 git bisect run ./test_script.sh 自动化
    • info frame 检查 saved rip 是否合法；x/s $rsp 看栈上的字符串数据；x/64gx $rsp 检查栈内存模式寻找被覆盖的模式（如全 0x41 说明被 'A' 覆盖）

    7.3 深挖方向¶

    • 崩溃收集 SDK 的设计：Breakpad/Crashpad 的 minidump 生成和符号服务（symbol server）
    • 崩溃聚类：如何对大量同质崩溃去重和优先级排序
    • 线上 post-mortem 分析的安全边界：core dump 可能包含敏感数据（密钥、用户信息）的加密和访问控制
