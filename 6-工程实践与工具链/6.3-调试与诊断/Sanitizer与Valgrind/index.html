    AddressSanitizer¶

    Note

    AddressSanitizer 只需加一个编译选项就能把"随机崩溃"变成"精确到行号的报错"——它是 C++ 内存排障的第一道防线。

    1. 知识点说明¶

    AddressSanitizer（ASan）是 Google 开发的编译期内存错误检测工具，已集成在 GCC（4.8+）和 Clang（3.1+）中。它通过编译器插桩和运行时 shadow memory 检测：堆/栈缓冲区溢出、use-after-free、use-after-return、double-free、内存泄漏（通过 LeakSanitizer 子组件）。ASan 的运行时开销约为 2x（CPU）和 2-3x（内存），远低于 Valgrind 的 10-50x，因此可以作为日常开发构建的默认选项。

    2. 核心概念¶

    • 编译期插桩：编译器在每次内存访问前插入检查代码——计算目标地址的 shadow 状态，如果不可访问则立即报错并终止。这不同于 Valgrind 的运行时二进制插桩
    • Shadow Memory 映射：将程序地址空间的每 8 字节映射为 1 字节的 shadow，值为 0 表示完全可访问，1-7 表示部分可访问（前 k 字节合法），负数表示不可访问（不同负数值编码不同的不可访问原因）
    • Redzone（红区）：在栈变量和堆分配块周围放置不可访问的 padding，一旦越界访问红区立即被捕获。堆 redzone 由 ASan 的 malloc 替换实现，栈 redzone 由编译器自动插入
    • Quarantine（隔离区）：free 后的内存不立即归还给 allocator，而是放入隔离区延迟释放。如果在隔离期访问这段内存，就能检测到 use-after-free。隔离区大小可配置

    3. 代码示例¶

    3.1 编译和运行¶

    # 编译：添加 -fsanitize=address，建议加 -g 定位行号，-O1 平衡性能和可调试性
g++ -fsanitize=address -g -O1 -o app main.cpp
./app

    3.2 检测堆越界¶

    int main() {
    int* p = new int[10];
    p[10] = 42;       // 越界！写入第 11 个元素
    delete[] p;
    return 0;
}

    ASan 输出： 

    ==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
WRITE of size 4 at 0x... thread T0
    #0 0x... in main main.cpp:3
0x... is located 0 bytes to the right of 40-byte region 0x...,0x...)
allocated by thread T0 here:
    #0 0x... in operator new[
    #1 0x... in main main.cpp:2

    3.3 检测 use-after-free¶

    int main() {
    int* p = new int(42);
    delete p;
    *p = 100;         // use-after-free
    return 0;
}

    ASan 输出： 

    ==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x...
WRITE of size 4 at 0x... thread T0
    #0 0x... in main main.cpp:4
0x... is located 0 bytes inside of 4-byte region [0x...,0x...)
freed by thread T0 here:
    #0 0x... in operator delete(void*)
    #1 0x... in main main.cpp:3

    4. 底层原理 / 实现机制¶

    Shadow Memory 编码方案：ASan 将程序地址空间的每 8 字节映射为 shadow memory 的 1 字节。映射公式：ShadowAddr = (Addr >> 3) + Offset（Offset 取决于平台，x86_64 下为 0x7fff8000）。Shadow 值含义：0 = 8 字节全部可访问；k (1-7) = 前 k 字节可访问，其余不可；负数编码不同错误类型（堆红区 = 0xfa、栈红区 = 0xf4、freed = 0xfd、全局红区 = 0xf9）。

    编译器插桩：每次内存访问（load/store）前，编译器生成类似以下逻辑： 

    if (ShadowAddr[Addr >> 3] != 0 && ((Addr & 7) + AccessSize) > ShadowAddr[Addr >> 3])
    __asan_report_error(Addr, AccessSize, IsWrite);
    实际生成的代码优化为两条指令（利用硬件影子内存检查），在 x86_64 上仅增加 ~73% 指令数。

    malloc 替换：ASan 提供自己的 malloc/free 实现。malloc(N) 实际分配 N + 2*redzone_size，前后各放置红区（填充 0xbe），返回地址居中。free(ptr) 将整个区域标记为 0xfd（freed）并放入隔离区。

    5. 常见问题¶

    编码陷阱¶

    • ASan + 其他 Sanitizer 不互斥但需注意顺序：-fsanitize=address,undefined 可以同时启用，但 ASan 和 TSan（ThreadSanitizer）不能同时用——两者都替换 malloc，冲突
    • ASan 的内存开销：每个 malloc 都会增加 redzone，大量小对象分配时内存消耗可能远超 3x。使用 ASAN_OPTIONS=quarantine_size_mb=64 调整隔离区大小
    • ASan 在 Release 构建中：-fsanitize=address 通常禁用了 -fomit-frame-pointer（需要栈回溯），且增加了 redzone，不适合最终的 production binary
    • 检测不到栈上的 use-after-scope（默认关闭）：-fsanitize-address-use-after-scope 启用，会延长栈变量的生命周期并在离开作用域后标记为不可访问

    概念误区¶

    • "ASan 和 Valgrind 可以互相替代" → ASan 检测栈越界（Valgrind 不检测）、速度快 10x+、需要重编译；Valgrind 检测未初始化值（ASan 的 MSan 才做）、不需要重编译。各有所长
    • "加了 ASan 的程序如果没报错就没内存问题" → ASan 只检测执行到的路径，未被覆盖的错误路径、逻辑错误（如错误的大小参数传给 memcpy 但仍在合法范围内）可能漏过

    6. 相关知识点¶

    • Valgrind — 二进制插桩的替代方案，互补使用
    • 内存泄漏 — 通过 LeakSanitizer 检测
    • 崩溃定位方法 — ASan 报错后的定位流程
    • GDB基础 — ASan 报错时可以配置 ASAN_OPTIONS=abort_on_error=1 让 GDB 捕捉崩溃现场

    7. 面试点¶

    7.1 高频问题¶

    • AddressSanitizer 的 Shadow Memory 映射原理：为什么 8 字节映射为 1 字节 shadow？
    • ASan 如何检测 heap-buffer-overflow？redzone 机制是什么？
    • ASan 和 Valgrind 的实现原理差异？各自适合什么场景？
    • ASan 如何检测 use-after-free？quarantine 隔离区的作用？
    • ASan 运行时 2x CPU 开销从哪来？为什么比 Valgrind 快那么多？

    7.2 回答要点¶

    • 每 8 字节对齐访问只需 1 字节 shadow（8 种状态：0 表示全可访问，1-7 表示部分可访问，负数表示不可访问），映射通过右移 3 位 + 偏移实现，shadow 地址计算只需几条指令
    • 编译器和 ASan 的 malloc 实现在每一块分配的内存周围插入不可访问的 redzone（填充特殊 magic 值），越界访问触发 shadow memory 检查 → 报错
    • ASan 是编译期插桩：编译器生成检查代码，需重编译，快（2x）；Valgrind 是二进制插桩：运行时翻译机器码，不需重编译，慢（10-50x）。ASan 还能检测栈越界和全局变量越界
    • free 后的内存不立即还给系统，放入隔离区（quarantine）延迟释放；隔离区内内存标记为 freed（shadow = 0xfd），访问即报 use-after-free；隔离区大小控制检测窗口和内存开销的平衡
    • 开销主要来自每次内存访问前的 shadow check（~73% 指令增量）和 malloc/free 的 redzone + quarantine 管理。比 Valgrind 快因为检查代码直接内联在目标代码中（无 IR 翻译开销），且利用硬件直接计算 shadow 地址

    7.3 深挖方向¶

    • ASan 的 false positive 来源：自定义栈展开、内联汇编中的内存操作
    • LeakSanitizer（LSan）的独立使用和与其他 Sanitizer 的集成
    • MemorySanitizer（MSan）检测未初始化值——ASan 不做的检查
    • HWASan（Hardware-assisted ASan）利用 ARM64 TBI 降低内存开销到 1%

    Sanitizer系列¶

    Sanitizers 是 LLVM/GCC 工具链提供的一组运行时检测工具，在编译时插入检查代码，在运行时捕获内存错误、数据竞争、未定义行为等问题。包括 AddressSanitizer(ASan)、ThreadSanitizer(TSan)、UndefinedBehaviorSanitizer(UBSan)、LeakSanitizer(LSan)、MemorySanitizer(MSan) 等。

    1. 知识点说明¶

    Sanitizers 是目前 C++ 排障工具链中最重要的运行时检查设施。相比 Valgrind 等纯二进制插桩工具，Sanitizers 在编译时插桩，在运行时只增加 1.5x~3x 开销（远低于 Valgrind 的 20x+），且定位精度极高——大多数问题能直接报告到源码行。

    五大 Sanitizer 分工明确： - ASan (AddressSanitizer)：捕获内存越界、use-after-free、double-free - TSan (ThreadSanitizer)：捕获数据竞争（多线程未同步访问共享变量） - UBSan (UndefinedBehaviorSanitizer)：捕获未定义行为（整数溢出、除零等） - LSan (LeakSanitizer)：捕获内存泄漏（通常集成在 ASan 中） - MSan (MemorySanitizer)：捕获未初始化内存读取

    2. 核心概念¶

    • 编译时插桩（Compile-time Instrumentation）：编译器在生成的代码中插入运行时检查点
    • 影子内存（Shadow Memory）：ASan 用额外的内存区域记录每字节的"状态"（可访问/已释放/红区）
    • 向量时钟（Vector Clocks）：TSan 内部用于跟踪 happens-before 关系
    • UB 分类：UBSan 检测 ~20+ 种 UB 类型，包括数组越界、空指针、符号溢出等
    • 假阳性（False Positive）：Sanitizer 可能误报，特别是 TSan 在特定内存序下

    3. 代码示例¶

    3.1 编译与运行¶

    # ASan — 检测内存错误
g++ -fsanitize=address -g -O1 -o test test.cpp
./test                       # 触发越界时，直接打印调用栈

# TSan — 检测数据竞争
g++ -fsanitize=thread -g -O2 -o test test.cpp -lpthread
./test                       # 报告竞争点

# UBSan — 检测未定义行为
g++ -fsanitize=undefined -g -O1 -o test test.cpp
./test                       # 检测到 UB 时报告

# 组合使用
g++ -fsanitize=address,undefined -g -O1 -o test test.cpp

    3.2 ThreadSanitizer 示例¶

    #include <thread>

int counter = 0;  // 全局变量，无保护

void increment() {
    for (int i = 0; i < 100000; ++i)
        ++counter;  // 数据竞争！
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    return 0;
}
// 编译: g++ -fsanitize=thread -g -O2 -o tsan_demo tsan_demo.cpp -lpthread
// 运行输出会定位到 ++counter 行，显示两个线程的访问栈

    3.3 UBSan 示例¶

    #include <iostream>

int main() {
    int x = 1;
    int shift = 31;
    x <<= shift;           // 有符号整数左移溢出 (UB)

    int y = -2147483648;
    y = -y;                 // 有符号整数负溢出 (UB)

    int* p = nullptr;
    *p = 42;                // 空指针解引用 (UB)

    int arr[4] = {0};
    arr[10] = 1;            // 数组越界

    return 0;
}
// 编译: g++ -fsanitize=undefined -g -O1 -o ubsan_demo ubsan_demo.cpp

    3.4 LSan（内存泄漏检测）¶

    void leak() {
    int* p = new int[100];  // 泄漏！
}

int main() {
    leak();
    return 0;
}
// ASan 默认包含 LSan。Linux 上 LSan 在进程退出时扫描
// 编译: g++ -fsanitize=address -g -O1 -o lsan_demo lsan_demo.cpp
// 运行: ASAN_OPTIONS=detect_leaks=1 ./lsan_demo

    4. 底层原理 / 实现机制¶

    ASan 工作原理¶

    ASan 在每个内存分配时在周围插入"红区（redzone）"，并将已释放的内存标记为"中毒（poisoned）"。影子内存中每 8 字节对应 1 字节的状态标记（可访问/红区/已释放）。每次内存访问前插入 inline check，如果影子内存标记异常则报告错误。

    TSan 工作原理¶

    TSan 维护每个内存位置和每个线程的访问历史（向量时钟 + 线程 ID）。当一个线程写、另一个线程读/写同一位置且没有通过锁或 atomic 同步时，TSan 报告数据竞争。

    UBSan 工作原理¶

    UBSan 在编译期识别 UB 的表达式，代入检查代码：除零检查、移位检查、有符号溢出检查等。检查失败时调用运行时报告函数。

    5. 常见问题¶

    编码陷阱¶

    • Sanitizer 之间可能冲突：ASan + TSan 不兼容，不能同时开启。UBSan 可与 ASan 或 TSan 组合
    • 运行时代价：ASan ~2x CPU + ~3x 内存；TSan ~5x CPU + ~10x 内存；UBSan ~1.2x CPU
    • 生产环境谨慎使用：Sanitizer 主要用于测试/CI，生产环境开启会显著降低性能
    • Windows 支持有限：MSan 和 TSan 在 Windows/MSVC 上支持不完整；Linux + Clang/GCC 是最好的平台

    概念误区¶

    • Sanitizers 不等于测试：它们是被动检测工具，覆盖率取决于测试代码执行的路径
    • Sanitizer 报告的行号需要 -g 调试信息：编译时务必加 -g 才能获得源码位置

    6. 相关知识点¶

    • AddressSanitizer — ASan 是 Sanitizer 家族中最常用的成员
    • Valgrind — 另一种运行时检测工具（二进制插桩，更慢但无需重编译）
    • GDB基础 — Sanitizer 定位问题后通常用 GDB 进一步分析
    • 崩溃定位方法 — Sanitizer 是崩溃定位的高效工具之一

    源3：Valgrind¶

    Valgrind¶

    Note

    Valgrind 不需要重新编译程序就能检测内存错误——代价是程序运行速度降低 10-50 倍，适合离线深度排查而非 CI 集成。

    1. 知识点说明¶

    Valgrind 是一套动态二进制插桩工具集，最常用的组件是 Memcheck——它通过模拟执行每条指令来检测：堆内存泄漏（malloc 无对应 free）、非法读写（越界、use-after-free）、未初始化值使用、重叠内存操作（memcpy 源和目标重叠）。其他工具包括：Callgrind（调用图和性能分析）、Helgrind（数据竞争检测）、Massif（堆分析器）。Valgrind 不需要重新编译目标程序，直接运行在已有的二进制上。

    2. 核心概念¶

    • 动态插桩 vs 编译期插桩：Valgrind 将目标程序的机器码转换为中间表示（VEX IR），插入检查代码后再转回机器码执行。AddressSanitizer 则是编译器在生成代码时插入检查。Valgrind 的优势是不需重编译，劣势是慢得多
    • Memcheck 的报告类型：definitely lost（确定泄漏，无指针指向）、indirectly lost（间接泄漏，容器结构被泄漏）、possibly lost（可能泄漏，内部指针）、still reachable（程序退出时仍可达，通常无害）
    • 未初始化值追踪：Memcheck 为内存的每个 bit 维护一个 V-bit（valid bit），写操作设置 V-bit，未初始化内存的 V-bit 为 0，当 V-bit 为 0 的值用于条件跳转或系统调用参数时报错
    • Suppression 文件：压制已知的误报（如 glibc 内部分配一次性内存），避免真实问题被噪音淹没

    3. 代码示例¶

    3.1 基本使用¶

    # 编译（不需要特殊选项，但 -g 有助于定位行号）
g++ -g -O0 -o app main.cpp

# 运行 Memcheck，带详细泄漏报告
valgrind --tool=memcheck --leak-check=full --show-leak-kinds=all ./app

# 典型输出
# ==12345== Invalid write of size 4
# ==12345==    at 0x4005A2: foo(int*) (main.cpp:10)
# ==12345==    by 0x4005D4: main (main.cpp:15)
# ==12345==  Address 0x5203044 is 0 bytes after a block of size 40 alloc'd
# ==12345==    at 0x4C2B9C7: malloc (vg_replace_malloc.c:299)
# ==12345==    by 0x40059E: foo(int*) (main.cpp:9)

    3.2 对应的 C++ 代码¶

    void foo(int* buf) {
    buf[10] = 42;    // 越界！buf 只分配了 10 个 int (40 bytes)
}

int main() {
    int* p = new int[10];
    foo(p);           // Memcheck 在此处报告 Invalid write
    // 忘记 delete[] p  → Memcheck 报告内存泄漏
    return 0;
}

    错误信息精确到行号，直接指向越界位置和分配位置。

    4. 底层原理 / 实现机制¶

    Valgrind 的架构：

    1. VEX IR 翻译：启动时 Valgrind 接管程序入口（_start），不执行原始机器码。它用 VEX 反汇编器将每个 basic block 的 x86/ARM 机器码转换为与架构无关的 VEX IR
    2. 插桩：在 VEX IR 上注入检查代码——每次内存访问前插入地址合法性检查（是否在已分配/mmap 范围内），每次值计算后更新 shadow V-bit
    3. JIT 执行：将插桩后的 IR 重新编译为目标平台机器码，缓存到 translation cache 中执行
    4. Shadow Memory：Memcheck 维护与程序地址空间 1:1 映射的 shadow memory，记录每个 byte 的分配状态（未分配/已分配不可访问/已分配可访问）和初始化状态（V-bit）

    内存检查的 shadow 状态：当 malloc 返回时，shadow 标记为 "已分配可访问但未初始化"。第一次写入后 shadow 变 "已初始化"。free 后 shadow 变 "不可访问"。后续读/写此地址即报 "use-after-free"。

    5. 常见问题¶

    编码陷阱¶

    • 把 "still reachable" 当成无害：虽不是严格泄漏，但大量 "still reachable" 表示全局容器无限增长，长时间运行的进程会 OOM
    • Valgrind + 多线程 = 串行化：Valgrind 的 JIT 执行是单线程的，多线程程序的竞态条件可能因时序改变而无法复现。数据竞争检测用 Helgrind 或 ThreadSanitizer
    • 误判未初始化值：编译器内联 memcpy 或 rep stos 等优化可能绕过 Valgrind 的跟踪，用 -O0 避免
    • 自定义内存分配器：不使用 malloc 的内存池，Valgrind 无法自动追踪。需要用 VALGRIND_MEMPOOL_* 宏告诉 Valgrind 分配语义

    概念误区¶

    • "Valgrind 能检测所有内存问题" → 不能检测栈缓冲区溢出（AddressSanitizer 可以）、不能检测静态内存的竞态、不保证检测到所有 leak（只检测到退出时仍不可达的）
    • "在 Valgrind 下通过的代码就没内存问题" → Valgrind 只检测运行到的路径，未被执行的代码路径上的内存问题不会报

    6. 相关知识点¶

    • AddressSanitizer — 编译期插桩的替代方案，速度快 2-5x 而非 10-50x
    • 智能指针 — unique_ptr/shared_ptr 从根本上杜绝 delete 遗漏
    • 内存泄漏 — 泄漏的类型和检测方法
    • strace — 系统调用追踪，与 Valgrind 互补

    7. 面试点¶

    7.1 高频问题¶

    • Valgrind Memcheck 和 AddressSanitizer 的实现原理差异？各自优缺点？
    • Valgrind 如何检测未初始化值的使用？V-bit 机制是怎样的？
    • "definitely lost"、"possibly lost"、"still reachable" 的区别？哪些是真正需要修复的？
    • Valgrind 为什么会让程序变慢 10-50 倍？

    7.2 回答要点¶

    • Valgrind 是二进制插桩（VEX IR 翻译 + JIT），不需重编译，但极慢（10-50x）；ASan 是编译期插桩，需重编译，但快（2-5x 开销），且能检测栈越界
    • Memcheck 为每 bit 内存维护 V-bit（shadow bit），写操作设 V-bit=1，读 V-bit=0 的值用于条件跳转/系统调用时报 "Conditional jump depends on uninitialised value"
    • "definitely lost"：无任何指针指向的泄漏块，必须修；"indirectly lost"：父结构泄漏导致子结构也泄漏，修好父结构即可；"possibly lost"：内部指针可能导致误判需人工确认；"still reachable"：全局指针仍持有，通常不是 bug 但需关注增长趋势
    • 每条指令都要反汇编→转 VEX IR→插桩→重编译 JIT→执行，且为每个内存操作维护 shadow 状态，指令膨胀巨大
